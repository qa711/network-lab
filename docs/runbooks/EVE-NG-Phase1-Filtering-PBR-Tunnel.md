# Task 1 — OSPF filtering on your real ABRs

You built genuine ABRs when the user SVIs moved to area 0.0.0.10. Site A's prefixes (10.1.0.0/24, 10.2.0.0/24, 10.4.0.0/24, 10.98.0.0/24) enter the backbone as Type-3 summaries generated by NEXUS-A. That boundary is where three of the four filtering methods live.

### 1.0 Baseline — know what you're about to remove

```
! PBR-B
show ip route 10.4.0.0 255.255.255.0        ! O IA, learned from area 0
show ip ospf database summary | i 10.4.0.0  ! the Type-3, advertised by 1.1.1.1 (NEXUS-A)
```

Expect both present. Every method below makes one or both disappear — the *which* is the lesson.

### 1.1 Method 1 — `area filter-list` at the ABR

Blocks the Type-3 from ever being **generated** into area 0. NX-OS flavour uses a route-map (IOS uses a prefix-list directly — know both for the exam).

```
! NEXUS-A
ip prefix-list PL-AREA10-OUT seq 5 deny 10.4.0.0/24
ip prefix-list PL-AREA10-OUT seq 10 permit 0.0.0.0/0 le 32
!
route-map RM-AREA10-OUT permit 10
  match ip address prefix-list PL-AREA10-OUT
!
router ospf 1
  vrf CISCO-CORP
    area 0.0.0.10 filter-list route-map RM-AREA10-OUT out
```

> IOS equivalent for your notes: `router ospf 1` → `area 10 filter-list prefix PL-AREA10-OUT out`

**Verify on PBR-B:** route gone **and** LSA gone — `show ip ospf database summary | i 10.4.0.0` returns nothing. The ABR never created it, so nobody in area 0 has it. Site-A VLAN40 is now unreachable inter-site (flows die at whichever hop runs out of route — note that PBR shifts the drop point but can't save a flow nobody can route).

Remove before the next method:
```
router ospf 1
  vrf CISCO-CORP
    no area 0.0.0.10 filter-list route-map RM-AREA10-OUT out
```
Confirm 10.4.0.0/24 returns on PBR-B.

### 1.2 Method 2 — `range … not-advertise` (summarisation as a filter)

Same observable, different mechanism: the range that *creates* the summary is told not to advertise it. You already have the range line — just re-enter it with the keyword:

```
! NEXUS-A
router ospf 1
  vrf CISCO-CORP
    area 0.0.0.10 range 10.4.0.0/24 not-advertise
```

Verify identical disappearance on PBR-B, then restore:
```
    area 0.0.0.10 range 10.4.0.0/24
```

Exam framing: method 1 is a *filter applied at the boundary*; method 2 is *the summarisation machinery itself* suppressing. Same result here because your ranges are 1:1 — with real aggregation they behave differently (a range hides components; a filter-list can kill the aggregate).

### 1.3 Method 3 — `distribute-list in` (the LSDB-vs-RIB demonstration)

The one the guide warns about, experienced. This filters **RIB installation only** — the LSA stays, the flooding continues, downstream routers still compute paths *through you*.

Deliberately using **10.1.0.0/24** (Vlan10, site A) here, not 10.2.0.0/24 — reason at the end.

```
! PBR-B
ip prefix-list PL-RIB-DENY seq 5 deny 10.1.0.0/24
ip prefix-list PL-RIB-DENY seq 10 permit 0.0.0.0/0 le 32
!
router ospf 1
 distribute-list prefix PL-RIB-DENY in
```

**Now read the three truths:**
```
! PBR-B — route gone from RIB:
show ip route 10.1.0.0 255.255.255.0          ! % Network not in table

! PBR-B — but the LSA is still right there:
show ip ospf database summary | i 10.1.0.0    ! present, untouched

! NEXUS-B — still trusts PBR-B completely:
show ip route 10.1.0.0/24 vrf CISCO-CORP      ! installed, next-hop 10.10.71.2 (PBR-B!)
```

Prove the blackhole:
```
! NEXUS-B
ping 10.1.0.1 vrf CISCO-CORP source 10.1.1.1   ! dies - AT PBR-B
```

NEXUS-B forwards to PBR-B because the LSDB says so; PBR-B has no route and drops. **That's why `distribute-list in` is dangerous on a link-state transit router** — you filtered your own RIB but kept advertising competence you no longer have.

*Why not 10.2.0.0/24?* Try it after, if curious: flows from 10.2.1.0/24 to 10.2.0.0/24 match PBR-ACL20 on Gi1, and **PBR is consulted before the RIB** — the policy forces next-hop 10.20.30.1 and the traffic sails straight over the hole. PBR masking a missing route is a great thing to have seen once (and a preview of Task 2's theme).

Cleanup:
```
router ospf 1
 no distribute-list prefix PL-RIB-DENY in
no ip prefix-list PL-RIB-DENY
```

### 1.4 Method 4 — filtering at redistribution (ASBR)

The guide's example, run for real. PBR-A becomes an ASBR:

```
! CORP-PBR-A
ip route 192.168.100.0 255.255.255.0 Null0
ip prefix-list REDIST-STATIC seq 5 permit 192.168.100.0/24
route-map STATIC-TO-OSPF permit 10
 match ip address prefix-list REDIST-STATIC
!
router ospf 1
 redistribute static subnets route-map STATIC-TO-OSPF
```

Verify it floods domain-wide as external:
```
show ip route ospf | i 192.168.100           ! on PBR-B: O E2
show ip route 192.168.100.0/24 vrf CISCO-CORP ! on CSW1: same
show ip ospf | i boundary                    ! PBR-A now reports ASBR
```

Now tighten the filter and watch the Type-5 get flushed:
```
no ip prefix-list REDIST-STATIC seq 5 permit 192.168.100.0/24
ip prefix-list REDIST-STATIC seq 5 deny 192.168.100.0/24
```
The E2 vanishes everywhere within seconds. Cleanup: remove the `redistribute` line, the static, the prefix-list and route-map.

### 1.5 Conditional debug — capture a full adjacency FSM

PBR-A has multiple OSPF neighbors; the condition keeps the noise down to one interface — that's the entire point of the technique.

```
! CORP-PBR-A
debug condition interface GigabitEthernet1
debug ip ospf adj
show debug condition          ! confirm the gate is set
```

Bounce the far end:
```
! NEXUS-A
interface Ethernet1/8
  shutdown
  no shutdown
```

**Expected on PBR-A:** only the Gi1 neighbor's events — DOWN, then INIT → EXSTART → EXCHANGE → LOADING → FULL (2-WAY flashes past on point-to-point). Write down which state does what; it's a favourite exam sequence. Then, always, in this order:

```
undebug all
no debug condition all
```

NX-OS side of the same story, no debug needed: `show ip ospf internal event-history adjacency` on NEXUS-A — the always-on flight recorder is the NX-OS answer to conditional debugging.

### 1.6 Stub/NSSA — why it's parked

Area 0.0.0.10 contains no routers other than the ABR itself (the DSWs are L2), so converting it to stub changes nothing observable — there's nobody inside to receive the injected default. It'll be a proper exercise in the 3-router pod (Phase 4).

# Task 2 — PBR grows reflexes: IP SLA + verify-availability

Current behaviour: `PBR-POLICY` seq 10 forces VLAN20-sourced inter-site traffic to CSW1 (10.10.30.1), seq 20 forces VLAN40 to CSW2 (10.10.60.1), seq 30 lets everything else route normally. If a next-hop dies, plain `set ip next-hop` only gives up when the interface goes down. Tracking makes each class fail over to the *other* core switch deliberately.

### 2.1 Probes and tracks

```
! CORP-PBR-A
ip sla 10
 icmp-echo 10.10.30.1 source-interface GigabitEthernet2
 frequency 5
ip sla schedule 10 life forever start-time now
ip sla 20
 icmp-echo 10.10.60.1 source-interface GigabitEthernet3
 frequency 5
ip sla schedule 20 life forever start-time now
!
track 10 ip sla 10 reachability
track 20 ip sla 20 reachability
```

```
! CORP-PBR-B — mirror
ip sla 10
 icmp-echo 10.20.30.1 source-interface GigabitEthernet2
 frequency 5
ip sla schedule 10 life forever start-time now
ip sla 20
 icmp-echo 10.20.60.1 source-interface GigabitEthernet3
 frequency 5
ip sla schedule 20 life forever start-time now
!
track 10 ip sla 10 reachability
track 20 ip sla 20 reachability
```

Confirm before touching the route-map: `show track brief` → both Up; `show ip sla statistics | i Latest` → return codes OK.

### 2.2 Swap the set clauses

```
! CORP-PBR-A
route-map PBR-POLICY permit 10
 no set ip next-hop 10.10.30.1
 set ip next-hop verify-availability 10.10.30.1 1 track 10
 set ip next-hop verify-availability 10.10.60.1 2 track 20
route-map PBR-POLICY permit 20
 no set ip next-hop 10.10.60.1
 set ip next-hop verify-availability 10.10.60.1 1 track 20
 set ip next-hop verify-availability 10.10.30.1 2 track 10
```

```
! CORP-PBR-B
route-map PBR-POLICY permit 10
 no set ip next-hop 10.20.30.1
 set ip next-hop verify-availability 10.20.30.1 1 track 10
 set ip next-hop verify-availability 10.20.60.1 2 track 20
route-map PBR-POLICY permit 20
 no set ip next-hop 10.20.60.1
 set ip next-hop verify-availability 10.20.60.1 1 track 20
 set ip next-hop verify-availability 10.20.30.1 2 track 10
```

Each class: primary next-hop gated by its track, backup gated by the other. Sequence numbers (1, 2) are the preference order.

### 2.3 Prove normal operation

Test traffic that matches the ACLs — source the pings from the site SVIs:

```
! NEXUS-A
ping 10.2.1.1 vrf CISCO-CORP source 10.2.0.1    ! matches PBR-ACL20 -> via CSW1
ping 10.2.1.1 vrf CISCO-CORP source 10.4.0.1    ! matches PBR-ACL40 -> via CSW2
```

```
! CORP-PBR-A
show route-map PBR-POLICY        ! match counters on seq 10 / seq 20 incrementing
show ip policy                   ! Gi1 -> PBR-POLICY
debug condition interface GigabitEthernet1
debug ip policy                  ! per-packet: "policy match" + "FIB policy route" lines
```
(`undebug all` / `no debug condition all` when done — it's per-packet.)

### 2.4 Break 1 — real failover

Start a long ping from NEXUS-A (`ping 10.2.1.1 vrf CISCO-CORP source 10.2.0.1 count 500`), then:

```
! CSW1
interface Ethernet1/5
  shutdown
```

**Expected:** a few drops while the probe times out (frequency 5s — a couple of cycles), then the stream continues. `show track brief` → track 10 **Down**, 20 Up. `debug ip policy` now shows the VLAN20 class using 10.10.60.1 — same policy, second next-hop. `no shutdown`, watch track 10 return.

### 2.5 Break 2 — everything down, and PBR fails *open*

No topology damage needed — point both probes somewhere unrouted (an SLA op must be deleted to change its target):

```
! CORP-PBR-A
no ip sla 10
ip sla 10
 icmp-echo 192.0.2.1 source-interface GigabitEthernet2
 frequency 5
ip sla schedule 10 life forever start-time now
no ip sla 20
ip sla 20
 icmp-echo 192.0.2.1 source-interface GigabitEthernet3
 frequency 5
ip sla schedule 20 life forever start-time now
```

Both tracks go Down — and the pings from NEXUS-A **keep working**. `debug ip policy` shows the tell: `policy rejected -- normal forwarding`. With every verified next-hop dead, PBR steps aside and the routing table carries the traffic. That's the behaviour the exam (and change reviews) ask about: tracked PBR degrades to normal routing, it doesn't blackhole.

Restore both SLAs to their real targets (10.10.30.1 / 10.10.60.1) the same delete-and-recreate way.

# Task 3 — the second GRE/IPsec tunnel (…60 path)

You pre-provisioned this without noticing: both PBRs already carry `network 172.16.12.4 0.0.0.3 area 0`, and the isakmp keys for the Gi3-side peers are in place (and correctly spelled, now). The OSPF adjacency will form the moment the tunnel exists — which makes it the perfect conditional-debug subject.

### 3.1 Arm the debug first

```
! CORP-PBR-A
debug condition interface Tunnel1
debug ip ospf adj
```

### 3.2 Build both ends

```
! CORP-PBR-A
interface Tunnel1
 description GREto-PBR-B-via-60path
 ip address 172.16.12.5 255.255.255.252
 ip mtu 1400
 ip tcp adjust-mss 1360
 tunnel source GigabitEthernet3
 tunnel destination 10.20.60.2
 tunnel protection ipsec profile GRE-IPSEC-PROFILE
```

```
! CORP-PBR-B
interface Tunnel1
 description GREto-PBR-A-via-60path
 ip address 172.16.12.6 255.255.255.252
 ip mtu 1400
 ip tcp adjust-mss 1360
 tunnel source GigabitEthernet3
 tunnel destination 10.10.60.2
 tunnel protection ipsec profile GRE-IPSEC-PROFILE
```

(`tunnel mode gre ip` is the default; sharing GRE-IPSEC-PROFILE across both tunnels is fine — each source/destination pair negotiates its own SAs.)

**Expected on PBR-A's debug:** IKE completes, Tunnel1 comes up, and the OSPF FSM scrolls past for the new neighbor only — the pre-existing `network 172.16.12.4` statement catches it with zero further config. `undebug all` / `no debug condition all`.

### 3.3 Verify the pair

```
show ip ospf neighbor                       ! new FULL neighbor on Tunnel1
show crypto session                         ! TWO sessions: peers 10.20.30.2 and 10.20.60.2
show crypto isakmp sa                       ! both QM_IDLE
show crypto ipsec sa | i peer|encaps|decaps ! counters on both peers
show ip ospf interface Tunnel1 | i Cost     ! ~1000 (default 100 kbps tunnel bandwidth)
```

That cost is why neither tunnel attracts transit traffic — physical paths cost single digits. The tunnels are overlay-in-waiting, exactly as designed.

While you're here, Tunnel0 on both ends is missing the MTU/MSS hardening — add it:
```
interface Tunnel0
 ip mtu 1400
 ip tcp adjust-mss 1360
```
(GRE adds 24 bytes, the IPsec transform another ~56 — without these, full-size TCP through the tunnel fragments or blackholes on PMTUD-hostile paths. A classic real-world GRE/IPsec gotcha.)

### 3.4 Break — phase-2 mismatch, and the diagnostic that names it

On one side only, wrap Tunnel1 in a deliberately wrong transform:

```
! CORP-PBR-B
crypto ipsec transform-set TS-WRONG esp-aes esp-sha256-hmac
 mode tunnel
crypto ipsec profile PROF-WRONG
 set transform-set TS-WRONG
!
interface Tunnel1
 tunnel protection ipsec profile PROF-WRONG
```

(Your live set is `esp-aes 256 esp-sha-hmac`; TS-WRONG differs in both cipher strength and hash, so the phase-2 proposal can't match.)

**Read the failure signature:**
```
show crypto isakmp sa                        ! peer 10.10.60.2 STILL QM_IDLE - phase 1 is fine
show crypto ipsec sa peer 10.10.60.2         ! no SAs / zero counters
show crypto session                          ! that peer: DOWN-NEGOTIATING
show interface Tunnel1 | i line protocol     ! down (protection configured, no SA)
```

**ISAKMP up + IPsec down = phase-2 problem** (transform or proxy mismatch). Compare with the phase-1 signature you've already lived through in this lab: a PSK mismatch never reaches QM_IDLE — it thrashes in MM_NO_STATE. You ran that experiment involuntarily with a mistyped key; now you know both failure faces on sight.

Restore:
```
! CORP-PBR-B
interface Tunnel1
 tunnel protection ipsec profile GRE-IPSEC-PROFILE
no crypto ipsec profile PROF-WRONG
no crypto ipsec transform-set TS-WRONG esp-aes esp-sha256-hmac
```

If you ran Phase 2 already and left PIM on Tunnel0, one line (`ip pim sparse-mode`) on each Tunnel1 keeps the tunnels symmetric.
